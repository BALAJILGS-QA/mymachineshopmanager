# Rollback / Recovery plan — Production Module migrations 0068–0073

**Golden rule:** if any migration fails, **STOP** — do not run the next one, do not attempt an
automatic rollback. Capture the exact error and use the per-migration recovery note below.
The only guaranteed full recovery is the **pre-migration backup/snapshot** (confirm it exists first).

All six migrations are **additive / non-destructive**: none drops a table or column, none deletes
or mutates existing rows. So a failure mid-way leaves earlier, already-applied migrations in a
valid, backward-compatible state — the **currently deployed app keeps working** because every new
object is additive and `transition_job` stays backward-compatible (see 0072).

## App-version compatibility (deploy ordering)

- **Migrations MUST be applied before the new app is deployed.** The new app references the new enum
  values, RPCs, tables, and storage buckets; without the schema it would error.
- **The migrated schema is compatible with the CURRENTLY deployed (old) app**, so the window between
  "migrations applied" and "new app deployed" is safe: old app only does legacy transitions, which
  the new `transition_job` still permits with no new permission requirement.
- Order: **backup → pre-check → 0068…0073 (validate each) → deploy app → smoke/RBAC/E2E/regression.**

## If `transition_job` behaves unexpectedly after 0072

Restore the prior definition by re-running `0003_job_rpcs.sql` (it is `create or replace` and
idempotent). This reverts to pre-slice production behaviour instantly without data loss.
