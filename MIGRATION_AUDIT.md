## 1. Current architecture

**Framework:** TanStack Start (SSR-capable) on **Vite 7**, with **TanStack Router** file-based routing. **Not Next.js.**

- Build tool: Vite 7.3.6 (`vite dev` / `vite build` / `vite preview`).
- App framework: `@tanstack/react-start@1.168.49` via the `tanstackStart()` Vite plugin (`vite.config.ts`).
- Router: `@tanstack/react-router@1.170.32`, file-based, generated tree at `src/routeTree.gen.ts`.
- Router bootstrap: `src/router.tsx` — `getRouter()` builds a fresh `QueryClient` + `createRouter()` per call (one instance per SSR request; single instance on client).
- Language: TypeScript 5.9.3, `strict: true`. **0** `.js`/`.jsx` files in `src` (71 `.tsx` + 55 `.ts`).
- Rendering model (two-tier):
  - **Public routes** (`/`, `/blog`, `/blog/$slug`) are **server-rendered** for SEO (`__root.tsx` emits `<HeadContent>` / `<Scripts>` and full meta/OG tags).
  - **Authenticated portal** (`/app/*`) is **client-only** — `src/routes/app/route.tsx` sets `ssr: false` so Supabase-session, `localStorage`, charts and PDF code never run on the server.
- **Deployment reality (important):**
  - **Vercel** (`vercel.json`): builds with `SPA=1 npm run build`, `outputDirectory: dist/client`, `framework: null`, and rewrites `/(.*) → /_shell.html`. → **Production on Vercel is a pure static SPA** (no SSR server running).
  - **Netlify** (`netlify.toml`): `npm run build`, `publish: dist`, SPA fallback to `/index.html`.
  - So although the codebase _can_ SSR, the live Vercel target today ships a client-rendered shell.

**Classification:** Vite + React + TanStack Start (hybrid SSR/SPA, currently SPA in production). Definitively **not** Next.js, **not** CRA.

## 5. Authentication architecture

- Implemented in `src/features/auth/auth.tsx` as a React **Context provider** (`AuthProvider` / `useAuth`) — client-side.
- **Dual backend:**
  - **Supabase mode** — email/password via Supabase Auth. User profiles + approval state stored in an `app_state` JSON blob (`app_state.data.users`), **not** a dedicated table. Super admins identified by email allowlist (`SUPER_ADMIN_EMAILS = ['admin@sreebalajiindustries.com']`).
  - **Local mode** — salted SHA-256 super-admin credential in `localStorage` (keys `cnc-shop-auth`, `cnc-shop-session`; default `superadmin` / `superadmin123`). Used when Supabase env vars are absent.
- **Roles:** `SuperAdmin` | `User`. **Registration-approval gate:** new sign-ups land as `pending` and cannot enter the app until a super admin approves.
- **Route guard:** `src/routes/app/route.tsx` — `AppLayout` reads `useAuth()`, shows a loader while `loading`, and `<Navigate to="/" replace />` when `!session`. Purely client-side gating (consistent with `ssr:false`).
- Supabase client (`src/data/supabase.ts`) configured with `persistSession`, `autoRefreshToken`, `detectSessionInUrl:false`, and a **pass-through lock** (bypasses Web Locks API to avoid cross-reload deadlocks).
- **Migration note:** all auth is browser-context today (localStorage + `crypto.subtle` + Supabase browser session). There is currently **no server-side session validation / middleware**. Moving to Next middleware-based protection is optional; the safe first step is to preserve the exact client gate inside a client layout.

## 13. Migration risks (ranked)

1. **`import.meta.env` → `process.env` / `NEXT_PUBLIC_*`** — used across supabase client + `lib/env.ts`. Every reference must change or the Supabase client silently becomes `null` (app falls back to local mode → looks like "data disappeared"). **High, pervasive.**
2. **Router rewrite (28 routes)** — TanStack file routes, `beforeLoad` redirects, `notFoundComponent` catch-alls, and typed `Link`/`useLocation` in `AppShell` all differ from Next `<Link>`/`usePathname`/`redirect()`. **High.**
3. **Client/server boundary** — jsPDF, Recharts, `crypto.subtle`, `localStorage`, Supabase browser session must not render on server. Mitigated by the existing `/app ssr:false` design, but every `/app` component tree needs `"use client"` discipline. **Medium.**
4. **Auth context timing** — `AuthProvider` + client route guard rely on client hydration order; Next's server/client split can flash or mis-gate if the guard runs server-side. **Medium.**
5. **QueryClient provider** — must be re-homed from router context to a Next client provider without changing cache defaults. **Medium.**
6. **Deployment mode flip** — Vercel currently serves a static SPA shell; Next introduces a server runtime. Vercel project settings (`framework`, build command, rewrites, headers) must be reconfigured; the `/_shell.html` rewrite must be removed. **Medium.**
7. **Brand rebrand (green → orange/charcoal)** — cosmetic but touches `tailwind.config.js` tokens + `AppShell` + every page; risk of inconsistency if not tokenised centrally. **Medium.**
8. **Forms rewrite to RHF+Zod** — InvoiceForm/JobForm/PaymentForm are complex; must preserve exact validation + calculation behaviour (cross-check against `computations.ts` + `repo.ts`). **Medium/High per-form.**
9. **E2E harness repoint** — Playwright `webServer` + specs assume Vite preview/SSR; false failures until repointed. **Low/Medium.**
10. **Dead deps activation** — RHF/`@hookform/resolvers` present but unused; no risk removing, but they signal intended (not-yet-real) design. **Low.**

## 14. Recommended migration sequence

Aligns with the master prompt's staged plan; each stage independently verifiable (typecheck + unit + build + relevant e2e must stay green):

1. **Foundation** — add Next (App Router) + `next.config`, keep Vite building in parallel; add `app/providers.tsx` (QueryClient + Auth + Toast/Confirm). Introduce `NEXT_PUBLIC_*` env plumbing behind a small `env` shim so both build systems read the same values.
2. **Public routes first** (lowest risk, already SSR-friendly): `/`, `/blog`, `/blog/$slug`, `/login`→`/`, `/signup`→`/` redirects. Verify SEO meta parity.
3. **App shell + auth** — port `AppShell` + `nav.ts` + `AuthProvider` into a client `app/app/layout.tsx`; reproduce the exact client route guard. Verify login/logout/refresh/protected-route.
4. **Portal routes, one module at a time** — jobs → materials → production → deliveries (+print) → invoices (+print) → payments → expenses → vendors → subcontracting → companies → approvals → sales → reports → settings, plus the 4 hub redirects. Verify each against Supabase before retiring the TanStack route.
5. **Browser-only features** — confirm jsPDF (challan/invoice), Recharts dashboard, exports work under client boundaries / dynamic import.
6. **Design system** — init shadcn/ui + Radix + tokens; rebrand to white/charcoal/orange; migrate primitives (see `UI_MIGRATION_MAP.md`).
7. **Forms** — migrate to RHF + Zod + zodResolver, form by form, preserving validation/calcs.
8. **Testing/perf/cleanup** — repoint Playwright; add regression specs; server/client optimisation; then remove Vite/TanStack per `CLEANUP_PLAN.md`.

## 18. Rollback strategy (per phase)

- Keep Vite + TanStack **fully working in parallel** until every route is migrated and verified; do not delete until `CLEANUP_PLAN.md` gates pass.
- One small reversible commit per module (see master-prompt git list); tag a known-good baseline before each phase.
- After each phase: `tsc --noEmit`, `vitest run`, production build, and the relevant Playwright spec must be green — else stop and revert that commit rather than stacking changes.
- Env changes behind a shim so a single revert restores the old `import.meta.env` path.
- Because production Vercel is a static SPA today, the pre-migration `dist/client` output remains a deployable fallback throughout.
